## 1. Why Plan 10

VeriFact exists for a phone user who wants a source-backed verdict, and for a reviewer who judges the architecture and the production habits behind it (PRD §1–2). The lead wants the resume story to cover **agent ops**: governance, monitoring, logging and traceability of a running agent system (roadmap §1).

The lead's picture of the reviewer's five minutes: **see the agents run, get an answer and evidence for a claim** in the app itself. The ops work supports that moment. It is not a second product.

Three facts from 2026-10-20 change the Phase E scope written on 2026-10-15:

1. **Quota is the binding constraint.** The free Gemini key allows 15 requests/minute and **500 requests/day** for `gemini-3.1-flash-lite`. A cold claim costs about 8 requests (about 5 worker model turns plus up to 3 grounded searches). About 50–60 cold claims fit in a day.
2. **The budgets in the code do not match that cap** (§2).
3. **A card-free host with enough memory does not exist** (§4, D1). The backend cannot be deployed always-on for free.

## 3. Goals, non-goals, anti-goals

**Goals**

- A request is **traceable end to end**: one id links the response header, every log line, the trace, the stored result and the audit record.
- The agent system is **governed in code, not only in prose**: a registry and a policy-to-test map that tests keep honest.
- The **Gemini daily cap is enforced as it really is** and survives restarts.
- A reviewer who never runs the code can still see the system work: a hosted frontend that shows real results, a **recorded demo** of the live pipeline, and trace/audit evidence in the README.
- The backend runs from **one command** in Docker, with measured memory and boot time.

**Non-goals (decided out of Plan 10)**

- A public, always-on backend. [lead]
- Live per-agent status in the frontend (event feed plus diagram change). Kept in project memory; compatible with the span design but **not** built here. [lead]
- Splitting the NLI/embedding models into separate services, or shrinking them with ONNX. Considered 2026-10-20, rejected for this plan: the RAM need moves rather than shrinks, and hosted inference tiers are small. [lead]
- A hosted trace viewer or a public audit view. [lead]
- Cloud Run or any host that needs a card. [lead]
- URL and screenshot input (Plan 8, runs after this plan). Scoring-engine changes. New agents.

**Anti-goals (a failure even if every task is green)**

- A trace, log or audit row that contains an API key, or claim/prompt/response text when content capture is off.
- A budget that can be overspent by restarting the process.
- A governance document nobody tests: every claim in the registry and the policy map is checked by a test, or is a named gap.
- A README that says "live demo" for something that is off most of the time. The README says what runs where.
- A fabricated or edited number: memory, boot time and quota figures come from real runs.

## 4. Decisions

| ID | Decision | Rationale |
|---|---|---|
| **D1 — R9** | **Demo-on-demand, no public backend.** [lead] The backend runs in Docker on the lead's machine with a one-command start. A Cloudflare Tunnel can expose the whole local stack when the lead wants to show it live. The public deliverables are the hosted frontend (D2), the recorded demo, and the README. | No card-free host offers ≥1 GB (searched 2026-10-20: free container tiers top out at 512 MB; Hugging Face Docker Spaces need a paid plan; Oracle's free VM asks for a card). About 60 cold claims/day would also exhaust an always-on public demo within minutes. Claims already in the database cost no quota. |
| **D2** | **Two APIs and a hosted frontend.** [lead] A small always-on **read API** serves `recent` and `result by id`; the heavy **verify API** (the existing backend) runs on demand. The frontend, hosted on a free static host, uses the read API all the time. Live checking exists only in the local stack. [lead on the split; the rest is my call] | Gives portfolio visitors a working site without a running backend. |
| **D2a** | **Read API = a Supabase Edge Function.** [lead: "sure"] It lives in the existing Supabase project, holds the service key server-side, mirrors the two existing endpoints' JSON exactly, and is public (`--no-verify-jwt`) with CORS limited to the frontend origins. Deployed by hand with the Supabase CLI, like migrations. A shared example-response fixture is checked by both a Python test (against `format_stored_result` / the recent-row shape) and a TypeScript test, so the two cannot drift. The formatting logic is **ported to TypeScript** (the shared fixture is the guard); a stored-response column is rejected because it would tie the database to an API shape and need a backfill. Abuse protection is parity with today's API plus `Cache-Control: public, max-age=60`, a clamped `limit`, UUID-only ids and CORS; there is no per-IP limit (Edge Functions have none built in), and the function never returns more than the existing endpoints do. [my call] | No new account or card. Free-plan Edge Function limits reported at 500K calls/month and 60 s runtime (third-party sources, unverified: confirm on supabase.com/pricing at plan time). |
| **D2b** | **The hosted frontend build disables live checking; the local-stack build enables it.** [my call] `VITE_READ_API_URL` and `VITE_VERIFY_API_URL` are added; both default to `VITE_API_BASE_URL` so existing setups still work. The hosted build leaves the verify URL empty; the claim box then shows a "Live checking runs in the local demo — watch the recording" state with links. In the local stack both point at the same origin (the web container), so a quick tunnel's random URL never has to be baked into a build. | A quick tunnel's address changes on every start. Same origin also removes CORS from the live path. |
| **D2d** | **One Supabase project; the lead curates the public feed.** [my call] The hosted site, the local stack and the smoke run share the project. `recent` shows only rows with `featured = true` (migration 07), so ordinary runs never appear on the public site by accident. The plan includes a curation step: the lead picks the demo claims, runs them in the local stack, and marks them featured with a documented SQL snippet. Eval runs persist nothing (`bypass_cache`). | An empty public feed would defeat D2. |
| **D2c** | Static host: **Vercel Hobby** (TDD §10 already names it). [my call] Confirm no card is asked at signup when the plan is executed; Cloudflare Pages is the fallback. | |
| **D3 — Quota** | **One shared Gemini request counter**, charged by worker model turns **and** by grounded-search sub-calls, default **`gemini_daily_request_budget = 400`** (about 50 cold claims; headroom for ADK retries and the lead's own use). [lead agreed to one counter and to persisting it; the number is my call] `llm_daily_call_budget` is removed from the defaults' meaning (kept as an alias with a deprecation note, then deleted in the docs); `search_daily_call_budget` stays as a secondary cap on grounded searches. Exhaustion degrades the agent to "Partial Analysis"; it never invents a score. A cache hit charges nothing. Eval runs keep zeroing budgets. | The two existing counters cannot see the real 500/day cap. |
| **D3b** | **Day boundary, granularity and headroom.** [my call] (a) The quota day follows the provider's reset, believed to be **midnight Pacific** (`plan9-evals-handoff.md` §7 flags this as unverified): a `quota_reset_tz` setting, default `America/Los_Angeles`, drives the day roll and the `daily_usage` key. The plan's first quota task verifies the reset time from Google's rate-limit documentation and records the source. The old UTC day stays for `search_daily_call_budget` only if the builder finds a reason. (b) The counter is charged **once per model turn**, on both the worker `LlmAgent`s and the grounded-search agent, through the same `before_model_callback` (the builder confirms the grounded agent can take it; if not, it charges once per search run). ADK's internal HTTP retries are **not** counted: accounting is approximate by design, and the 100-request headroom below 500 absorbs retries. (c) The counter sees only traffic that goes through the backend. Eval runs (budgets off), manual API use and the lead's other uses of the key are uncounted, and the headroom is the buffer for them. The lead adjusts `GEMINI_DAILY_REQUEST_BUDGET` for the day when a record run or recording is planned, and the demo runbook (D11) does the arithmetic. | Exact request counting would need hooks below ADK; the cap is a protection, not billing. |
| **D3a** | **The counter survives restarts via write-behind persistence.** [lead agreed to persistence; the mechanism is my call] Charging stays in-process and synchronous (no database round trip on the critical path). The count is loaded from a `daily_usage` table at startup and at the UTC day roll, and increments are written to it in the background (the existing persistence task pattern, flushed at request end and at shutdown). If the table is unreachable, the in-process count is authoritative and a warning is logged; the budget never fails open to "unlimited". | A per-charge database call would add about a second to a cold request; a single-instance deployment does not need it. |
| **D4 — Tracing** | **OpenTelemetry via ADK's built-in spans plus custom spans for what ADK cannot see**: cache lookup, grounded search, page fetch, NLI scoring, scoring, persistence. Every span carries outcome (`ok`, `degraded`, `timeout`, `budget_refused`, `error`) and the model id where there is one. Export is OTLP/HTTP to **Phoenix running in the Docker Compose stack** (open source, no account). Prompt/response/claim text is **off** by default and enabled only by `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS` for a deliberate local capture. [lead: local Phoenix and README screenshots are enough] | ADK 2.12 already instruments the agents, so Plan 10 configures and extends instead of rebuilding. OTLP keeps the viewer swappable. |
| **D5 — Request id and logs** | A request id is accepted from a sane `X-Request-Id` (≤64 chars of `[A-Za-z0-9._-]`) or generated (UUID4), echoed in the response header, set as a root-span attribute `verifact.request_id`, put on every log record through a context variable, stored on the result row, and stored in the audit record. Logs are one JSON object per line (timestamp, level, logger, message, request_id, trace_id, agent where known). The `request_timing` line becomes a structured record. [my call] | Whether the request id *is* the trace id (when it is 32 hex chars) or only an attribute is left to the builder; the requirement is that one search finds all four artefacts. A span attribute is enough for the Phoenix side: finding the trace by `verifact.request_id` in the Phoenix UI is documented in the runbook and checked by hand once in the smoke run; the automated test checks the in-memory span exporter. The background persistence task is created inside the request context (`asyncio.create_task` copies context variables), so its spans become children of the request trace and carry the same id. |
| **D6 — Registry** | **Agent registry as data**: one file (YAML or a Python module; builder's call) with a row per agent — supervisor, `factcheck`, `crossref`, `linguistic`, grounded-search sub-agent: purpose, model setting name, tools and per-tool call caps, thinking/turn limits once Task A lands, timeout setting, budget counters charged, data read/written, failure mode and neutral value, owner test. Tests fail if a workflow node, tool or agent has no row, or a row names a setting or tool that does not exist. The human-readable page `docs/governance/agent-registry.md` is **generated** from the file. [my call] | A registry that tests keep honest cannot go stale silently. |
| **D7 — Policy map** | **Policy-to-test map as data**: one entry per enforced control — spend budgets, per-agent timeouts, request deadline, rate limit, SSRF guard (page fetch and, later, URL input), prompt-injection fencing, input sanitisation/rejection, AllSides-only bias labels, confidence capping, degradation honesty, retention purge, RLS lockdown, secrets never logged or traced, trace content off by default. Each entry names the enforcing code and the tests that prove it. A test fails if a named test does not exist. A control with no proving test is listed as a **gap** with an owner and a plan task, never dropped. [my call] | This is the "each tied to the test that proves it" scope from the roadmap, made checkable. |
| **D8 — Audit record** | **One `run_audits` row per request**, written in the same background persistence step as the result: request id, result id, time, app version (`APP_VERSION` set at image build, `dev` otherwise), model ids (`model_id`, `search_model_id`), a short hash of each agent's instruction text (the prompt version) and tool list, per-agent outcome (status, duration, model turns, tool calls by name, error code), cache outcome (`hit`/`miss`/`bypass`, and the source result id on a hit), the shared-counter value before and after, and the settings that bound the run (timeouts, caps). **No claim text**: join to `results` / `claims` for that. Purged with the same 90-day retention. **Scope** [my call]: a row for every request that reaches the cache or the workflow, written in the same shielded background task as persistence, so it still lands when the response was cut at the request deadline. That includes cache hits, degraded runs, budget refusals inside agents, and `AllAgentsFailedError` (then with `outcome = all_agents_failed` and no result id). Requests rejected before the workflow (400, 422, 429) get log lines only. `cache = bypass` marks `bypass_cache=True` calls (the eval harness and tests); those persist nothing, so they write no audit row either. Stored only; readable by the lead in Supabase, not exposed by any endpoint. [lead: stored only] | Table design follows migration conventions: RLS on, no policies. |
| **D9 — Packaging** | `backend/Dockerfile` (CPU-only torch; embedding, NLI and spaCy models baked into the image so a start needs no download), a `docker-compose.yml` with `backend`, `web` (serves the built frontend and proxies `/api` to the backend: one origin), and `phoenix`; a start script; a tunnel runbook (`cloudflared tunnel --url` for the `web` port; the quick-tunnel limits of 200 in-flight requests and no server-sent events are documented). Peak memory and cold-boot time are measured inside the container and written into TDD §10. [my call] | The TDD's "about 2 GB" is an estimate; the measured figure replaces it. |
| **D10** | **Supabase keep-alive**: a scheduled GitHub Action (daily) calls the read API's `recent` endpoint, which queries the database. No secret is needed because the function is public. [my call] | The backend is usually off; frontend traffic alone cannot be relied on. |
| **D11** | **Recorded demo is a deliverable.** [lead] The lead records it; the plan supplies a **runbook**: the claims to use (including at least one that degrades honestly and one served from cache), the start state (cleared day counter or known value), a quota reserve for retakes (about 10 cold claims = 80 requests), and where the video goes (GitHub README, portfolio site). | |
| **D12** | **Deployed-eval smoke only.** The roadmap's "run the eval suite against the deployed URL" becomes one short smoke run through the local stack (2–3 claims, about 16–24 requests, with the lead's OK for the spend) proving traces, logs and audit rows appear. The full eval run is Plan 9's and is not repeated. [my call] | Quota. |

## 6. Workstreams and what each must prove

Each becomes one or more plan tasks with a test-first step. Order follows dependencies, not this list.

1. **Quota (D3, D3a).** Migration `08` (`daily_usage`; `results.request_id`; `run_audits` may share it or get `09`, builder's call). Shared counter; the grounded-search call path charges it; write-behind persistence with load at startup and day roll. *Proves:* a restart mid-day keeps the count; a database outage does not fail open; search sub-calls consume the same budget as worker turns; eval harness still runs with budgets off.
2. **Request id and logs (D5).** *Proves:* one request's log lines, response header, stored row and root span share one id; a malformed `X-Request-Id` is replaced; no key or claim text appears in a log line from the verify path.
3. **Tracing (D4).** Add the OTLP/HTTP exporter dependency with `uv`; call ADK's provider setup at startup only when an endpoint is configured; custom spans; spans for degraded and refused outcomes. *Proves:* an in-memory span exporter in a test sees the expected tree for a cold request, a cache hit, a degraded agent and a budget refusal; content attributes are absent by default. *First step is a spike:* confirm ADK's spans reach Phoenix with the app's own `InMemoryRunner` (setup is normally done by ADK's own server, not by a custom FastAPI app). If they do not, set the provider explicitly.
4. **Governance (D6, D7).** Registry and policy map files, drift tests, generated page, gap list. *Proves:* adding an unregistered tool or agent fails a test; deleting a proving test fails a test.
5. **Audit record (D8).** *Proves:* one row per request including cache hits, degraded runs and budget refusals; no claim text; purged with retention.
6. **Read API and frontend (D2, D2a, D2b).** Edge Function, shared fixture and tests, frontend base-URL split, "live checking offline" state (designed with `DESIGN.md` and the impeccable skill, Plan 7's error-state patterns), hosted build. *Proves:* a stored result and the recent list render from the read API alone, backend off; the offline state shows in the hosted build; the shared fixture matches both implementations. (Frontend work goes to the frontend agent with a written brief, as in Plan 7.)
7. **Packaging and deployment (D9, D10, D12).** Dockerfile, compose, start script, tunnel runbook, keep-alive workflow, measured memory and boot time, one smoke run. *Proves:* `docker compose up` brings the stack to a healthy state from a clean machine; the image needs no network for models; the smoke run produces a Phoenix trace, JSON logs and an audit row.
8. **Demo kit and docs (D11, §9).** Runbook, README "Agent ops" section (what runs where, trace screenshot, registry and policy-map links, an audit-row sample, the measured figures), TDD/PRD/roadmap/plans-README updates. The README's status line is changed only after the work is verified.
9. **Gate.** `code-reviewer` and `eval-guardian` on the whole branch; `uv run pytest` (backend) and `pytest eval/tests` green offline; frontend `npm run lint && npm run build` and its tests; no live calls except the D12 smoke run.

## 7. Constraints

- `uv` only. The scoring engine (`backend/app/scoring/`) is untouched. Bias labels come only from AllSides; confidence capping stays; English only.
- Task A (latency, thinking budgets, date awareness) edits `backend/app/agents/*` and `config.py` on its own branch. Plan 10 starts after it merges, or rebases onto it. The plan is written assuming Task A has merged: its setting names (thinking budgets, turn caps) are read from the merged code when the plan is executed, and the registry rows for them are filled in then. If Plan 10 must start earlier, it branches from `main`, the registry rows for those limits read `pending Task A`, and the D8 "model turns" field counts `before_model_callback` firings, which is correct either way. Expect a small `config.py` merge with Plan 9's `eval_judge_model`.
- Plan 10 starts while Plan 9's live runs are on hold. [lead] Nothing in Plan 10 needs live quota except D12. The harness change (budgets off) must not break Plan 9.
- No code, no live calls and no `.env` reads happen in this design step. Plan execution later: never commit `.env`, `*-handoff.md`, `AGENTS.md`, `.claude/`, `.agents/`. Migrations are applied by the lead by hand, in order.
